# ADR 006：多知识库、切片编辑与版本回滚

## 背景

单知识库控制面已经具备上传、异步索引、切片浏览和召回诊断，但无法创建用途不同的知识库，
也不能修正单个索引切片或恢复历史原文件版本。现有聊天页面不得因此改变主体布局，且旧的
`tests/docs_test`、SQLite 目录和 Qdrant collection 必须继续可用。

## 决策

- SQLite 新增知识库注册表。管理 API 统一使用
  `knowledge_base_id / resource` 嵌套路由，所有目录查询在知识库边界内执行。
- 每个知识库独占一个 Qdrant collection、活动文档目录、版本目录和后台服务队列。这一方案
  在当前本地 Qdrant 部署中提供直观的删除边界和故障定位。
- 默认知识库由原配置自动登记，继续使用原文档目录和 collection。SQLite 启动迁移把旧版
  `source_path` 全局唯一约束改为知识库内复合唯一，不复制或删除用户数据。
- 手工切片编辑只允许活动文本切片。客户端提交读取时的正文 SHA-256；服务端匹配后重新调用
  当前知识库嵌入模型，并用同一个 Qdrant point 原子覆盖正文、元数据和向量。SQLite 只保存
  编辑前后哈希和定位信息，不复制敏感正文。
- 原文件版本保持不可变。回滚不是直接复用可能已经删除的旧向量，而是创建持久化后台任务，
  重新解析目标原文件并生成新向量文档；完成后切换活动版本。
- 现有聊天 Agent 仍绑定默认知识库。新增知识库只在管理控制面和召回测试中使用；聊天侧的
  知识库绑定和会话持久化需要另行设计。

## 未采用方案

1. 所有知识库共享一个 collection，仅依赖 metadata filter：当前删除、对账和本地运维更难
   审计，错误配置的影响范围也更大。
2. 手工编辑后修改原文件：PDF、Word、PPTX 和 Excel 无法可靠把切片正文反写到源格式，
   也会破坏不可变版本语义。
3. 回滚直接恢复旧向量标识：替换索引成功后旧向量会被删除，直接复用不能保证数据仍存在。

## 影响与限制

- 每个知识库一个 collection 会增加 collection 数量，达到大规模知识库数量前应重新评估
  共享 collection、远程 Qdrant 和分布式任务协调。
- 回滚和重新索引会替换手工编辑结果；界面必须在回滚确认中明确提示。
- 聊天继续使用默认知识库，因此本次变更不会改变聊天主体、Composer 或 assistant-ui
  Runtime 契约。
