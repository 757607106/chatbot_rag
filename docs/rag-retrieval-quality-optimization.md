# RAG 检索准确率优化复盘：从模式混答到章节感知与重排序

## 1. 背景与问题

测试问题：

> 本地打印模式怎么设置模板

错误回答把“本地打印模式”和“Web 打印模式”视为同一种模式，采用了 Web 模式的
“打印按钮下拉 → 自定义编辑”入口，并与本地模式的页面设置、报表属性混合输出。

知识原文并不缺失，且两个入口有明确区别：

- 本地打印模式：打印管理器界面点击【模板编辑】。
- Web 打印模式：点击打印按钮右侧下拉箭头，再点击【自定义编辑】。

因此，这不是单纯的生成模型知识错误，而是检索上下文在进入模型前已经丢失了模式边界。

该问题只作为最小反例。修复目标是建立与具体产品和问法无关的 RAG 准确率契约，代码中
不允许出现“遇到本地打印就选择某段内容”一类问题关键词分支。

## 2. 定位方法

本次按以下链路逐层取证：

1. 核对原始知识，确认正确答案是否存在。
2. 查看 Parser 输出的 `Section` 边界。
3. 查看 Chunk 文本是否保留父级标题。
4. 使用线上同款查询、Embedding 和 Qdrant 读取实际排名。
5. 对照最终回答引用的原文，判断错误发生在召回还是生成阶段。

修复前，问题的实际向量 Top 5 为：

| 排名 | 分数 | 内容范围 |
| --- | ---: | --- |
| 1 | 0.743089 | Web 模式报表设置 |
| 2 | 0.726192 | Web 模式自定义编辑入口 |
| 3 | 0.725900 | 本地模式页面设置，但块内缺少父级模式标题 |
| 4 | 0.689128 | 本地模式报表属性，但块内缺少父级模式标题 |
| 5 | 0.684212 | 只有图片说明的低信息块 |

真正包含本地模式入口的块只排在第 23 名，分数为 `0.634401`。运行时只注入
Top 5，生成模型没有得到正确入口，却同时看到了多个模式的局部内容，最终发生跨模式拼接。

## 3. 根因

### 3.1 图片被误用为语义边界

旧版 `MarkdownMediaParser` 每遇到一张图片就结束当前 `Section`。图片后的正文虽然
属于同一标题章节，却成为一个没有父级标题的新 Section。

### 3.2 Chunk 不跨 Section，Overlap 无法补救

AgentScope 2.0.5 约定 Chunker 不跨 `Section` 合并。`chunk_overlap=64` 只对同一
Section 内的长度切分有效，无法把前一个 Section 中的“本地打印模式”补到图片后的块。

参考：[AgentScope 2.0.5 RAG 文档](https://docs.agentscope.io/versions/2.0.5/zh/building-blocks/rag)。

### 3.3 单阶段向量排序偏向局部语义相似

向量检索更容易把“设置打印模板”“报表设置”等局部措辞相似的块排在前面，但不会稳定
保证“本地”和“Web”这类短而关键的限定词决定最终顺序。

### 3.4 Prompt 只能作为最后防线

旧提示词要求“忠于知识库”，但没有明确禁止跨产品、版本、模式和终端合并步骤；当检索
失败时，中间件仍会继续调用生成模型，也缺少“无当前轮检索内容必须拒答”的硬约束。

### 3.5 测试覆盖了管线正确性，没有覆盖答案正确性

原测试可以证明 Parser 能登记图片、文档能入库、RAGMiddleware 被正确装配，却不能证明
“本地打印”问题一定召回本地模式入口。结构测试和冲突场景回归用例缺失，使问题没有在
提交前暴露。

## 4. 方案与取舍

### 4.1 Markdown 按标题建立自然章节

图片只在原位置替换为内部媒体引用，不再创建 Section。Parser 在代码围栏之外识别
Markdown 标题，正文按标题自然边界拆分，并把完整标题路径写入
`retrieval_context` 元数据。

示例：

```text
# 云辉煌打印手册
## 1、云辉煌本地打印模式
### 1.2、设置打印模板
```

这样，本地和 Web 的同名“设置打印模板”小节天然属于不同 Section，不会相互污染。

### 4.2 每个最终 Chunk 保留自包含范围

`ContextPreservingChunker` 包装 AgentScope `ApproxTokenChunker`：

1. 所有格式都写入真实文档来源。
2. Markdown 在来源之后写入完整标题路径。
3. PDF 同时写入页码，Word 等无标题结构的格式至少保留来源。
4. 长章节被继续切分时，为后续每个 Chunk 重复完整范围。

这一步既解决同一长 Section 后续 Chunk 再次失去标题的问题，也避免 Word、PDF 的候选
脱离原文后只能由模型猜测所属文档。

### 4.3 接入 qwen3-rerank

查询链路调整为：

```text
用户问题
  -> 移除中间件说话人标签
  -> text-embedding-v4 + Qdrant 召回 Top 50
  -> 移除内部 <chatbot-media> 标记
  -> 给每个候选补充真实文档来源
  -> qwen3-rerank 问答相关性精排
  -> 最终 Top 5
  -> RAGMiddleware
  -> 生成模型
```

重排序 instruct 使用英文，并明确要求：

- 候选内容必须能够直接回答问题；
- 逐项匹配问题中明确出现的对象、属性、版本、环境与适用条件；
- 任一显式条件冲突的候选都不能视为答案。

阿里云官方建议先召回 50–100 个候选，再重排筛选 Top 5–10；`qwen3-rerank` 单次支持
最多 500 个文档、单文档最多 4,000 Token、单请求最多 120,000 Token，适用于文本语义
检索和 RAG。参考：[百炼重排序文档](https://help.aliyun.com/zh/model-studio/rerank)。

本项目选择候选 Top 50、最终 Top 5，在官方建议范围内，同时控制延迟和请求规模。
精排成功后只返回模型确认的候选及其相关性分数，不为凑满 Top K 补回未经精排的向量
候选。这样能够防止低质量内容绕过重排序重新进入生成上下文。

### 4.4 重排序失败策略

qwen3-rerank 调用异常时不返回空上下文，而是记录服务端异常并回退到原始向量 Top 5。
原因是 AgentScope 静态 RAG 在知识库搜索异常时会继续调用生成模型；返回已有向量候选
比让模型在完全无资料时回答更安全。

针对实际验证中出现的 TLS EOF 和握手超时，网络异常会在单次 15 秒超时内最多尝试两次。
重试有明确上限；两次都失败才执行向量回退，避免瞬时抖动轻易绕过重排序。

向量检索本身没有结果时，系统提示要求固定说明知识不足，不得使用历史回答或常识补全，
也不得输出“无匹配内容”等伪来源。

### 4.5 为什么不只调大 Top K

正确入口原来排在第 23 名。把 Top 5 改成 Top 10 仍无法命中；直接改成 Top 25 又会把
更多互相冲突的模式内容交给生成模型，增加上下文噪声和推理成本。扩大候选集必须配合
重排序，而不是直接扩大最终注入量。

### 4.6 为什么不只改 Prompt

Prompt 无法恢复未被召回的正确入口，也无法可靠识别已经丢失的父级标题。正确顺序是：

1. 修复知识结构；
2. 提高候选召回；
3. 使用重排序提高精度；
4. 最后用 Prompt 约束冲突处理和拒答。

### 4.7 生成参数和通用边界

事实型知识问答将聊天模型 `temperature` 从 `0.7` 降为 `0.1`，降低同一证据下的随机
扩写。系统提示不再枚举“本地、Web”等样例词，而是要求逐项核对问题中的所有显式条件。
同一套实现适用于产品、版本、地域、部门、角色、时间和运行环境等冲突，不依赖业务词表。

## 5. 实现落点

| 文件 | 职责 |
| --- | --- |
| `rag/media_parsers.py` | 图片原位替换、Markdown 标题章节和完整标题路径 |
| `rag/contextual_chunker.py` | 为所有格式的最终 Chunk 保留来源、标题或页码范围 |
| `models/reranker.py` | DashScope `qwen3-rerank` 请求、响应校验和安全错误 |
| `rag/reranking_knowledge_base.py` | 扩大向量候选、调用重排序、回退向量排序 |
| `agents/chat_agent.py` | 通用显式条件核对、无检索拒答和来源真实性约束 |
| `models/model_factory.py` | 使用低随机性的事实问答生成参数 |
| `config/settings.py` | 重排序模型和候选数量配置校验 |
| `rag/document_ingestor.py` | 提升摄取管线版本，确保旧索引自动重建 |

新增直接依赖固定为 `dashscope==1.26.5`，避免通过 AgentScope 的传递依赖隐式使用 SDK。

## 6. 验证结果

### 6.1 自动化验证

新增或扩展的测试覆盖：

- Markdown 图片不再切断正文顺序；
- 标题路径能够区分本地和 Web 同名小节；
- 代码围栏中的井号不会误判为标题；
- 长章节的每一个 Chunk 都重复标题路径；
- Word/PDF 等无 Markdown 标题的块仍保留来源，PDF 同时保留页码；
- 向量查询和重排序查询都不包含中间件说话人标签；
- qwen3-rerank 请求参数、instruct、结果映射和异常响应；
- 瞬时网络异常执行一次重试，持续失败后才进入回退；
- 候选从 50 条精排到最终 Top K；
- 内部图片标记不会发送到重排序模型；
- 精排成功后不会补入未经重排序的候选；
- 重排序服务失败时回退向量结果；
- 系统提示使用通用显式条件契约，不包含问题样例关键词；
- 对象与版本、年份与对象、地域与属性三类冲突场景中，正确证据即使位于向量第 23 名
  也能进入最终结果。

最终验收结果为 `62 passed`，分支覆盖率 `86.60%`；`mypy` 严格检查、`flake8` 和
`git diff --check` 全部通过。

### 6.2 真实模型验证

使用当前 `DASHSCOPE_API_KEY` 和项目的通用显式条件指令调用 qwen3-rerank，对以下两个
候选做连通性与排序方向冒烟验证：

| 候选 | qwen3-rerank 分数 |
| --- | ---: |
| 本地打印模式：打印管理器界面点击模板编辑按钮 | 0.858135 |
| Web 打印模式：点击打印按钮旁的自定义编辑 | 0.660411 |

为避免只验证这一道题，又使用同一真实 qwen3-rerank 接口增加三组互斥候选；三组正确
证据都排在第一：

| 冲突维度 | 正确候选分数 | 最高冲突候选分数 |
| --- | ---: | ---: |
| 产品与版本 | 0.962719 | 0.836146 |
| 年份版本与对象 | 0.910916 | 0.670076 |
| 地域与指标属性 | 0.963128 | 0.576542 |

重排序的职责是保证直接证据排序靠前，不保证固定 Top K 内完全没有主题相关但范围冲突的
内容。因此生成契约还必须尊重检索顺序：先使用排名最靠前且直接回答问题的证据，后续
候选只有在全部适用条件一致时才能补充。

修复后的端到端回答已正确输出：

> 在打印管理器界面点击【模板编辑】按钮，进入打印模板编辑界面。

引用来源恢复为真实的 `云辉煌打印.md`，未再把本地模式等同于 Web 模式。

验证期间出现过 DashScope Embedding TLS `UNEXPECTED_EOF_WHILE_READING`。该情况被
识别为外部服务瞬时失败，不是召回排序回归；隔离验证中系统按新提示拒绝根据常识补答。
生产环境仍应监控 Embedding、Rerank 和 Chat 三段调用的失败率与耗时。

## 7. 可复用优化流程

遇到“知识明明存在但回答错误”时，按以下顺序处理：

### 第一步：建立最小反例

- 固定一个问题、正确答案、禁止出现的答案片段。
- 明确产品、版本、模式、环境、时间等限定词。
- 不先改 Prompt，先保留错误回答和引用作为证据。

### 第二步：检查知识原文

- 确认正确内容确实存在且没有互相矛盾。
- 对冲突内容标记各自适用范围。
- 若原文错误，先修知识，不在检索层打补丁。

### 第三步：查看 Section 和 Chunk

- 输出每个 Section 的自然边界和元数据。
- 检查每个 Chunk 是否自包含：脱离前后文后仍能知道所属范围。
- 特别检查图片、表格、分页和附件是否意外切断标题上下文。

### 第四步：记录实际召回

- 使用线上同款 query、Embedding、向量库和 Top K。
- 记录排名、分数、来源、Chunk 索引和关键预览。
- 正确块不在候选集：修切分、上下文或扩大候选召回。
- 正确块在候选集但排序靠后：增加重排序或混合检索。

### 第五步：验证重排序

- 候选数应明显大于最终 Top K。
- 选择问答模式还是相似度模式必须与产品场景一致。
- 用互斥范围的最小候选对做真实模型冒烟测试。
- 校验返回索引、越界、重复、空结果和超时。

### 第六步：约束生成

- 明确只使用当前轮检索内容。
- 明确不得合并互斥范围。
- 来源名称必须来自检索元数据。
- 无足够知识时拒答并省略来源列表。

### 第七步：形成回归闭环

- Parser 测试保证自然边界。
- Chunker 测试保证上下文自包含。
- Reranker 测试保证候选精排与失败回退。
- 真实模型只做受控冒烟，不放入离线单元测试。
- 变更切分语义时必须提升摄取管线版本并重建索引。

## 9. 后续触发条件

以下需求出现时再单独评估进一步架构升级：

- 大量型号、单号、错误码需要精确匹配：增加 BM25/全文检索，与向量候选融合后再重排。
- 需要按图片内容检索：升级多模态 Embedding 与 `qwen3-vl-rerank`。
- 多轮问题大量使用“它”“上一个”等指代：增加独立查询改写，不把历史全文直接作为查询。
- 多用户并发：先完成 AgentScope 会话隔离，避免不同用户历史上下文互相污染。
